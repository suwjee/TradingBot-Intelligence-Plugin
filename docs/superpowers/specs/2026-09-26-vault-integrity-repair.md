# Vault Integrity Repair Specification

## Goal

Repair the TradingBot Knowledge Vault and its read-only Intelligence Plugin so
their executable integrity checks, retrieval boundaries, and written evidence
describe the current inspected state without changing Production.

## Scope

Only these repositories may change:

- `D:\My-Projects\TradingBot-Knowledge`
- `D:\My-Projects\TradingBot-Intelligence-Plugin`

`D:\My-Projects\TradingBot` is read-only. Its Engine source, directional
references, RAW files, sidecars, source hashes, and working-tree state must not
be changed. Do not create a worktree. Preserve the user-owned untracked
`TradingBot-Knowledge/_GENERATED/` directory.

## Decisions

### Fixture source-review contract

Case notes may optionally declare
`source_fixture_review: "pending-manual-review"`. Absence retains the strict
current behavior. A missing fixture source, unsafe fixture path, malformed
fixture metadata, or an undeclared source SHA-256 mismatch is an error. A
declared `pending-manual-review` source SHA-256 mismatch is reported as
`KNOWN_PENDING` and a warning; it does not rewrite the stored expected SHA,
source line, source body, or fixture assertion. A declared marker on a matching
fixture source does not generate a pending result.

The builder remains strict for all non-declared evidence. Its check mode may
succeed with reported `KNOWN_PENDING` warnings, while real errors still return
nonzero. The Plugin independently exposes `errors`, `warnings`, and
`known_pending`; `failures` remains an alias of `errors` for compatibility.
`ok` is true only when there are no errors and the physical RAW inventory is
complete. `verified_pins_ok` is true only when there are no errors or unresolved
known-pending fixture source pins. `data_status` distinguishes `PASS`,
`PASS_WITH_WARNINGS`, and `FAIL`.

None of the current 22 fixture notes receives the new marker, and none of their
existing SHA-256 values changes, because their shared current fixture source
matches now.

### Knowledge boundary

`algorithm.order.a` remains canonical and retrievable. `algorithm.order.b` and
`algorithm.order.c` remain retained, non-canonical, known-invalid,
`pending-fix`, excluded from default retrieval and normative reasoning, but
available through explicit quarantined retrieval. Their notes state exactly:
`Correct future semantics are not yet defined.`

OrderAudit remains present only inside byte-exact source snapshots and optional
reference evidence. It must not be an indexed knowledge entity, conceptual
pipeline stage, default retrieval concept, fixture authority, normative
dependency, or accepted trading rule.

### Evidence and data wording

`behavior.s.blue.type3` receives behavior-level documentation only. It will
describe the source/reference-supported order-free, post-A-stop S Blue route,
while linking to the algorithm note and source evidence rather than inventing a
new trading rule.

Data documentation must state the verified current Vault inventory: seven
physical RAW files, five physical sidecars, and three reproducible logical
windows. Historic inspection language may remain only when it explicitly
distinguishes those logical windows from physical files. RAW bytes, sidecars,
hashes, and window boundaries do not change without a separately proven error.

The frontmatter guide must reflect the real JSON Schema: all notes carry the
field, but a non-system `normative`, `canonical`, or `executable` note needs a
nonempty engine source reference. Policy, registry, and aggregate notes are not
given fabricated anchors.

### Generated material

Only `_SCHEMA/build_indexes.py` writes `_INDEX` outputs. `_INDEX` is never
hand-patched. The generator will run twice after source knowledge changes and
the resulting generated bytes must be identical. Do not create or complete
knowledge for `09_CASES`, `10_DECISIONS`, `11_VERSIONS`, `12_WORKFLOWS`, or
`13_PLUGIN`. The intentionally deferred Leg remains deferred.

## Required Verification

Run Python compilation checks, schema/build checks in knowledge and full-data
modes, deterministic index generation, relevant Vault-generator tests, Plugin
reader and maintenance tests, VaultReader and CLI smoke tests, MCP smoke tests
when its dependency is present, direct source-snapshot comparisons for all nine
Engine modules, reference identity checks for Bullish and Bearish HPZR6, and
final Git-status verification for all three repositories.

`READY_FOR_NEXT_PHASE` may be reported only if no real integrity error remains.
Known-invalid Order_B/Order_C, a future manual-review capability, intentionally
deferred Leg, and a Production-only pre-existing `sync_review_state=needs_review`
do not independently block that verdict.
